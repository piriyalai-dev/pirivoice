# บทที่ 27 ภาคผนวกทางเทคนิค

ภาคผนวกทางเทคนิคนี้จัดทำขึ้นเพื่ออธิบายชื่อทางเทคนิคที่ปรากฏในคู่มือ ในบันทึกการใช้งาน และบนหน้าจอ ให้กลับมาอ้างอิงถึงเรื่องเดียวกันได้ ครอบคลุมชื่อสิทธิ์ ชื่อตารางฐานข้อมูล ชื่อฟิลด์ ค่าสถานะ และปลายทางบริการ (API Endpoint) ที่ไม่มีปุ่มให้กดบนหน้าจอ การอ้างอิงในบทนี้จึงเป็นกุญแจสำหรับผู้ที่ต้องตอบคำถามว่าค่าที่เห็นในฐานข้อมูลหรือในบันทึกมีความหมายอย่างไร

ลักษณะสำคัญของภาคผนวกทางเทคนิค มีดังนี้

1. **การตอบคำถามทางเทคนิค:** ใช้เมื่อต้องตอบว่าค่าที่เห็นในฐานข้อมูลแปลว่าอะไร
2. **การอ้างอิงจากโค้ดจริง:** ทุกรายการในบทนี้อ้างจากโค้ดจริง มิใช่ชื่อที่แต่งขึ้นใหม่
3. **สำหรับผู้ตอบคำถามทางเทคนิค:** ผู้ปฏิบัติงานประจำวันไม่จำเป็นต้องอ่านบทนี้ ภาคผนวกมีไว้ตอบคำถามทางเทคนิคเท่านั้น

## 27.1 กลุ่มผู้ใช้งานและขอบเขตของบท

ผู้ที่ใช้บทนี้ได้แก่ ผู้ดูแลระบบ ครูสภานักเรียน ประธานสภา และผู้พัฒนาที่ต้องตอบคำถามทางเทคนิค โดยใช้สิทธิ์เดิมของคู่มือภาคนี้ มิได้เพิ่มสิทธิ์ใหม่แต่อย่างใด ก่อนเริ่มใช้งาน ควรเปิดคู่มือภาคที่ 2 คู่ไว้ด้วย เพราะภาคผนวกนี้มิได้สอนงาน หากแต่ต่อชื่อทางเทคนิคเข้ากับคำที่บทเหล่านั้นใช้

## 27.2 รหัสสิทธิ์กับคำที่ใช้บนหน้าจอ

ระบบเก็บสิทธิ์เป็นรหัสภาษาอังกฤษไว้ในชุดข้อมูลสิทธิ์ (Permissions) ของสมาชิก แล้วใช้ค่าเดียวกันเปิดหรือปิดเมนู หน้าจอมิได้แสดงรหัสนี้ ผู้ใช้งานเห็นเพียงว่าเมนูนั้นแสดงหรือไม่แสดง โดยรหัสสิทธิ์พร้อมความหมายและสิ่งที่ปลดล็อกบนหน้าจอ สรุปไว้ในตารางที่ 27.1

**ตารางที่ 27.1** แสดงรหัสสิทธิ์ ความหมาย และสิ่งที่ปลดล็อกบนหน้าจอ

| รหัสสิทธิ์ | ความหมาย | สิ่งที่ปลดล็อกบนหน้าจอ |
|---|---|---|
| `SUBMIT_ISSUE` | แจ้งเรื่องได้ | ปุ่ม **“แจ้งเรื่อง”** |
| `VIEW_OWN_ISSUES` | ดูเรื่องของตนเอง | แท็บ **“เรื่องของฉัน”** |
| `RECEIVE_ISSUES` | รับเรื่องในระดับที่ดูแลอยู่ | ปุ่ม **“รับเรื่อง + ตั้งเวลา”** |
| `MANAGE_ISSUE_STEPS` | เพิ่มและปิดขั้นตอนในเรื่อง | ส่วน **“ขั้นตอนการดำเนินงาน”** |
| `SET_COUNTDOWN` | ตั้งและยืดกำหนดแก้ไข | ปุ่มตั้งวัน และ **“ยืดเวลา”** |
| `ESCALATE_ISSUE` | ส่งต่อเรื่องขึ้นระดับบน | เมนู **“ส่งต่อไประดับบน”** |
| `VIEW_LEVEL_PYRAMID` | เห็นเรื่องในระดับที่ดูแลอยู่ | คิว **“ที่รับผิดชอบ”** |
| `MANAGE_ANNOUNCEMENTS` | สร้าง แก้ และปลดระวางประกาศ | เมนู **“จัดการประกาศ”** |
| `MANAGE_EVENTS` | สร้างกิจกรรมและสแกนเช็คอิน | แท็บ **“จัดการ”** ในหน้า **“กิจกรรม”** |
| `MANAGE_STUDENTS` | ดูและแก้ข้อมูลนักเรียนในขอบเขตที่ดูแลอยู่ | **“สมาชิก”** **“นำเข้านักเรียน”** **“ย้ายห้องนักเรียน”** |
| `VIEW_DASHBOARD` | เปิดแดชบอร์ด | เมนู **“แดชบอร์ด”** |
| `MANAGE_SETTINGS` | ตั้งปีการศึกษา ภาคเรียน และระบบ | **“ปีการศึกษา”** **“ภาคเรียน”** |
| `VIEW_AUDIT_LOG` | เปิดบันทึกการใช้งาน | เมนู **“บันทึกการใช้งาน”** |

อีกกลุ่มหนึ่งที่มีหน้าตาคล้ายชื่อสิทธิ์แต่ไม่ใช่ ได้แก่ ค่าที่ขึ้นต้นด้วย `READ_` เช่น `READ_ISSUES` `READ_STUDENTS` `READ_ME` และ `READ_DASHBOARD_TRAFFIC` ค่าเหล่านี้คือชื่อการอ่านที่ระบบบันทึกไว้ในบันทึกการใช้งานเมื่อมีผู้เปิดหน้านั้น มิได้หมายความว่าต้องมีสิทธิ์ตัวนี้ก่อน หน้าจอใช้สิทธิ์ตัวอื่นในการเปิดอยู่แล้ว และการบันทึกการอ่านเป็นแบบพยายามอย่างเต็มที่ หากบันทึกพลาด คำขอยังสำเร็จตามปกติ

ค่า `is_admin` มิใช่สิทธิ์รายข้อ แต่เป็นแฟล็กที่บอกว่าให้ข้ามการตรวจสิทธิ์ทั้งหมด ค่านี้มาจากตำแหน่งใน `backend/config/roles.json` จึงไม่มีหน้าจอให้ตั้งแยก ตำแหน่งที่ติดแฟล็กนี้ ได้แก่ ประธานสภา ครูสภานักเรียน และผู้ดูแลระบบ

ค่า `SUPER_ADMIN_ID` ในไฟล์ตั้งค่าของระบบเป็นรหัสผู้ใช้งานที่ข้ามทุกด่านเช่นเดียวกัน ใช้เมื่อต้องกู้ระบบในกรณีที่ไม่มีผู้ที่ติดแฟล็กนี้เข้าสู่ระบบได้ และตั้งได้ครั้งละหนึ่งคน

## 27.3 ชื่อตารางฐานข้อมูลที่คู่มือกล่าวถึง

คู่มือภาคที่ 2 เขียนด้วยคำที่หน้าจอใช้ ตารางนี้จึงเป็นคู่มือย้อนกลับสำหรับผู้ที่พบชื่อในฐานข้อมูล โดยชื่อตาราง สิ่งที่จัดเก็บ และชื่อที่ใช้ในคู่มือภาคที่ 2 สรุปไว้ในตารางที่ 27.2

**ตารางที่ 27.2** แสดงชื่อตารางฐานข้อมูล สิ่งที่จัดเก็บ และชื่อที่ใช้ในคู่มือภาคที่ 2

## 27.4 ค่าสถานะที่เก็บในฐานข้อมูล

ค่าสถานะถูกเก็บเป็นภาษาอังกฤษ ส่วนหน้าจอแปลเป็นภาษาไทยทุกครั้งที่แสดง ค่าสถานะของแต่ละกลุ่มข้อมูล มีดังนี้

เรื่อง ใช้ค่า `pending` แปลว่ารอรับเรื่อง `in_progress` แปลว่ากำลังดำเนินการ `escalated` แปลว่าส่งต่อให้ระดับสูงขึ้น `resolved` แปลว่าแก้ไขเสร็จ `rejected` แปลว่าถูกปฏิเสธ และ `cancelled` แปลว่าถูกยกเลิก

บอร์ด ใช้ค่า `active` แปลว่าใช้งานอยู่ `closed` แปลว่าปิดประเด็น และ `hidden` แปลว่าถูกซ่อน

รายงานเนื้อหา ใช้ค่า `open` แปลว่ารอจัดการ `resolved` แปลว่าซ่อนแล้ว และ `dismissed` แปลว่าไม่ดำเนินการ

ประกาศ ใช้ระดับความสำคัญ ได้แก่ `normal` `high` และ `urgent` ส่วนการปลดระวางดูจาก `retired_at` ที่มีค่าหรือว่าง มิใช่คอลัมน์สถานะ

กิจกรรม ใช้ค่า `draft` แปลว่าฉบับร่าง `published` แปลว่าเผยแพร่แล้ว และ `cancelled` แปลว่ายกเลิกแล้ว ส่วนการลบแยกจากสถานะและดูจาก `deleted_at`

การลงทะเบียนกิจกรรม ใช้ค่า `registered` แปลว่าลงทะเบียนแล้ว `waitlisted` แปลว่าคิวสำรอง `checked_in` แปลว่าเช็คอินแล้ว และ `cancelled` แปลว่ายกเลิก

งานนำเข้า Excel ใช้ค่า `PENDING` แปลว่ารอคิว `QUEUED` แปลว่าเข้าคิวแล้ว `PROCESSING` แปลว่ากำลังประมวลผล `COMPLETED` แปลว่าเสร็จแล้ว และ `FAILED` แปลว่าล้มเหลว

รอบการเลื่อนชั้น ใช้ค่า `PREVIEWED` แปลว่าดูแผนแล้ว `APPLIED` แปลว่าดำเนินการแล้ว และ `FAILED` แปลว่าล้มเหลว

## 27.5 การลบที่มิได้ลบข้อมูลจริง

ข้อมูลที่ต้องตอบย้อนหลังได้ ถูกลบโดยการติดเวลาไว้ที่ `deleted_at` เท่านั้น แถวยังคงอยู่ในตาราง และทุกหน้าจอยังกรองแถวนั้นออก เพราะเงื่อนไขค้นหาทุกรายการมีข้อกำหนดว่า `deleted_at` ต้องว่าง

ผลที่ตามมามีสองประการซึ่งพบในงานจริงบ่อย ได้แก่

1. ข้อมูลที่ลบแล้วยังกินพื้นที่และยังนับเป็นแถวในตาราง หากตัวเลขในฐานข้อมูลมากกว่าที่หน้าจอแสดง ให้พิจารณาข้อนี้ก่อน
2. การกู้คืนทำได้โดยล้าง `deleted_at` ให้ว่าง หน้าจอไม่มีปุ่มนี้ ต้องใช้เครื่องมือฝั่งเทคนิค

ประกาศมีอีกชั้นหนึ่งคือ `retired_at` ซึ่งแปลว่าการนำออกจากหน้าเว็บแต่ยังเก็บไว้เป็นประวัติ สองคอลัมน์นี้เป็นอิสระต่อกัน หากปลดระวางแล้วลบ แล้วกู้คืนกลับมา จะกลับมาเป็นปลดระวางแล้วตามเดิม

รูปมีรอบเก็บกวาดต่างจากข้อมูลทั่วไป โดยการลบรูปติด `deleted_at` ก่อน แต่ไฟล์จริงยังอยู่บนดิสก์จนกว่าสคริปต์ `backend/scripts/purge_media.py` จะทำงาน ค่าเริ่มต้นเก็บไว้ 30 วันตาม `MEDIA_PURGE_AFTER_DAYS` จึงยังกู้คืนได้ในช่วงนั้น สคริปต์ยังเก็บกวาดไฟล์ที่ไม่มีแถวอ้างถึงซึ่งเก่ากว่า 24 ชั่วโมงด้วย ทั้งนี้ต้องรันแบบทดลองก่อนเสมอ แล้วจึงใส่ `--apply`

> **ข้อควรระวังสำคัญ:** การลบกับการปลดระวางเป็นคนละเรื่อง หากต้องการให้ประกาศหายจากหน้าเว็บแต่ยังดูย้อนหลังได้ ให้ใช้การปลดระวาง มิใช่การลบ แม้การลบจะกู้คืนได้ก็จริง แต่ระหว่างนั้นประกาศจะหายจากทั้งหน้าเว็บและรายการในหน้าจัดการ

## 27.6 บันทึกการใช้งานที่เขียนพร้อมการเปลี่ยนแปลงข้อมูล

ทุกคำขอที่เขียนข้อมูลจะเขียนแถวลงใน `audit_logs` ภายในชุดการทำงานเดียวกันกับการเปลี่ยนแปลงข้อมูล หากการเปลี่ยนแปลงล้มเหลว ชุดการทำงานทั้งก้อนจะถูกยกเลิก และบันทึกก็หายไปด้วย ผลคือบันทึกกับข้อมูลตรงกันเสมอ ไม่มีกรณีใดกรณีหนึ่งจากสองกรณีต่อไปนี้หลุดรอดไปได้

1. บันทึกระบุว่าสำเร็จ แต่ข้อมูลมิได้เปลี่ยน
2. ข้อมูลเปลี่ยนแล้ว แต่ไม่มีบันทึกว่าใครเป็นผู้ทำ

การกระทำที่มีชื่อในบันทึก และเหตุการณ์ที่เกิด มีสรุปไว้ในตารางที่ 27.4

**ตารางที่ 27.4** แสดงชื่อการกระทำในบันทึกการใช้งานและเหตุการณ์ที่เกิด

| ชื่อในบันทึกการใช้งาน | เกิดเมื่อใด |
|---|---|
| `ACCEPT_ISSUE` | กดรับเรื่องและตั้งกำหนด |
| `ESCALATE_ISSUE` | ส่งต่อเรื่องขึ้นระดับบน |
| `CHANGE_DESTINATION` | เปลี่ยนปลายทางของเรื่อง |
| `RESOLVE_ISSUE` | ปิดเรื่อง |
| `REASSIGN_ISSUE` | มอบหมายเรื่องให้ผู้รับใหม่ |
| `APPROVE_TO_PUBLIC` | อนุมัติเรื่องขึ้นบอร์ดสาธารณะ |
| `HIDE_BOARD` · `HIDE_COMMENT` | ซ่อนกระทู้หรือความคิดเห็น |
| `REPORT_COMMENT` | มีผู้กดแจ้งเนื้อหา |
| `RESOLVE_REPORT` | ปิดรายงานว่าซ่อนแล้วหรือไม่ดำเนินการ |
| `MOVE_STUDENTS` | ย้ายนักเรียนเข้าห้องหรือออกจากห้อง |
| `APPLY_ROLLOVER` | กดยืนยันการเลื่อนชั้น |

ชื่อเต็มทุกตัวอยู่ใน `audit_logs.action` ซึ่งเปิดดูได้ที่หน้า **“บันทึกการใช้งาน”** โดยเลือกคอลัมน์การกระทำ

## 27.7 ปลายทางบริการที่ไม่มีปุ่มบนหน้าจอ

บางงานมีปลายทางบริการให้เรียกใช้งานแล้ว แต่หน้าจอยังไม่มีปุ่ม ต้องใช้เครื่องมือฝั่งเทคนิคหรือให้ผู้ดูแลระบบดำเนินการให้ โดยปลายทาง หน้าที่ และเหตุผลที่ไม่มีปุ่ม สรุปไว้ในตารางที่ 27.5

**ตารางที่ 27.5** แสดงปลายทางบริการที่ไม่มีปุ่มบนหน้าจอ พร้อมหน้าที่และเหตุผล

| ปลายทางบริการ | หน้าที่ | เหตุผลที่ไม่มีปุ่ม |
|---|---|---|
| `POST /api/boards/{board_id}/unhide` | เปิดกระทู้ที่ถูกซ่อนคืน | กันการกดผิดบนหน้าจอที่เห็นกันทั่วไป |
| `POST /api/boards/{board_id}/comments/{comment_id}/unhide` | เปิดความคิดเห็นที่ถูกซ่อนคืน | เหตุผลเดียวกับกระทู้ |
| `PATCH /api/students/{student_id}` | แก้ชื่อ นามสกุล คำนำหน้า เลขที่ และรหัสนักเรียน | หน้าจอแก้ได้เฉพาะตำแหน่ง หากจะแก้ชื่อให้ใช้การนำเข้า Excel แทน |

ทุกปลายทางบริการใช้การตรวจสิทธิ์แบบเดียวกับหน้าจอ หากบัญชีไม่มีสิทธิ์จะได้รับการตอบกลับเป็นรหัส 403 มิใช่ทำงานให้อย่างเงียบ ๆ

## 27.8 ปลายทางบริการของรูปภาพ

รูปทุกใบส่งผ่านลิงก์ที่ลงลายมือชื่อ (Signed URL) กำกับซึ่งหมดอายุ 15 นาที ตาม `MEDIA_URL_SIGNING_TTL_SECONDS` ลายเซ็นผูกกับรหัสรูป ผู้ดู และเวลาหมดอายุ หากแก้ค่าในลิงก์จะได้รับการตอบกลับเป็นรหัส 403 หน้าจอจึงขอชุดลิงก์ใหม่เมื่อรูปหมดอายุ มิได้ใช้รหัสผ่านชั่วคราวในการเปิดไฟล์ ปลายทางบริการของรูปภาพสรุปไว้ในตารางที่ 27.6

**ตารางที่ 27.6** แสดงปลายทางบริการของรูปภาพและหน้าที่

| ปลายทางบริการ | หน้าที่ |
|---|---|
| `POST /api/issues/{issue_id}/images` | อัปโหลดรูปหลักฐานหรือรูปความคืบหน้าของเรื่อง สูงสุดสามรูปต่อชนิด |
| `GET /api/issues/{issue_id}/images` | ดูรายการรูปของเรื่อง พร้อมลิงก์ที่ลงลายมือชื่อ |
| `DELETE /api/issues/{issue_id}/images/{image_id}` | ลบรูปในเรื่อง |
| `POST /api/media/{owner_type}/{owner_id}` | อัปโหลดรูปให้เจ้าของที่รองรับ |
| `GET /api/media/{owner_type}/{owner_id}` | ดูรายการรูปของเจ้าของนั้น |
| `DELETE /api/media/{owner_type}/{owner_id}/{image_id}` | ลบรูปของเจ้าของนั้น |
| `GET /api/media/file/{image_id}` | ส่งไฟล์รูปจริง พร้อมตรวจสิทธิ์ซ้ำทุกครั้งที่ส่ง |

ข้อจำกัดของรูปมาจากไฟล์ตั้งค่าของระบบ ได้แก่ ขนาดไฟล์ใหญ่สุดสิบเมกะไบต์ตาม `MEDIA_IMAGE_SIZE_LIMIT_MB=10` ด้านยาวสุด 1600 จุดภาพตาม `MEDIA_MAX_DIMENSION=1600` และคุณภาพ WebP 80 ตาม `MEDIA_WEBP_QUALITY=80` รูปจะถูกย่อขนาดและล้างข้อมูล EXIF โดยอัตโนมัติก่อนจัดเก็บ มิได้เก็บไฟล์ต้นฉบับ

## 27.9 ข้อจำกัดและข้อควรระวัง

ภาคผนวกทางเทคนิคมีข้อจำกัดและข้อควรระวังที่ควรทราบ ดังนี้

1. ภาคผนวกนี้อ้างจากโค้ด ณ วันที่เขียน หากโค้ดเปลี่ยนแล้วคู่มือไม่ตาม ให้ยึดการทำงานจริงของระบบเป็นหลัก
2. ชื่อตารางและฟิลด์ห้ามนำไปใช้เป็นชื่อที่เขียนในคู่มือภาคที่ 1 และภาคที่ 2 ให้คงคำที่หน้าจอใช้
3. การแก้ข้อมูลในฐานข้อมูลโดยตรงโดยไม่ผ่านปลายทางบริการ จะไม่มีบันทึกการใช้งาน ใช้เป็นทางสุดท้ายเท่านั้น
4. ค่าที่มีตัวพิมพ์ใหญ่ทั้งคำ เช่น `PENDING` และ `APPLIED` เป็นของงานนำเข้าและงานเลื่อนชั้น ส่วนค่าตัวพิมพ์เล็กเป็นของเรื่อง บอร์ด และกิจกรรม
5. มิควรเปลี่ยนรหัสสิทธิ์ใน `roles.json` โดยไม่ตรวจฝั่งหน้าจอ เพราะเมนูผูกกับรหัสโดยตรง

## 27.10 แนวทางการแก้ไขปัญหาที่พบบ่อยในการใช้งาน

ในระหว่างการใช้ภาคผนวกทางเทคนิค ผู้ปฏิบัติงานอาจพบปัญหาที่พบบ่อย ซึ่งมีแนวทางการแก้ไขสรุปไว้ในตารางที่ 27.7

**ตารางที่ 27.7** แสดงแนวทางการแก้ไขปัญหาที่พบบ่อยในการใช้งานภาคผนวกทางเทคนิค

| ปัญหาหรือสถานการณ์ที่พบ | สาเหตุและแนวทางการแก้ไข |
|---|---|
| เจอค่าสถานะในฐานข้อมูลที่ไม่ตรงกับที่หน้าจอแสดง | หน้าจอแปลค่าทุกครั้งที่แสดง ให้ดูตารางค่าสถานะในบทนี้ หากมิใช่ค่าที่อยู่ในตาราง แสดงว่ามีโค้ดรุ่นใหม่ที่ยังมิได้อัปเดตคู่มือ |
| บันทึกการใช้งานมีแถวที่ข้อมูลมิได้เปลี่ยนจริง | บันทึกถูกเขียนในชุดการทำงานเดียวกันกับการเปลี่ยนแปลง หากพบลักษณะดังกล่าว ให้ตรวจสอบว่าแก้ข้อมูลผ่านปลายทางบริการหรือแก้ในฐานข้อมูลโดยตรง เพราะการแก้นอกปลายทางบริการจะไม่มีบันทึก จึงเกิดภาพกลับด้านได้ |
| ลบประกาศแล้วยังเห็นข้อมูลในฐานข้อมูล | เป็นการทำงานปกติ การลบในระบบนี้เพียงติดเวลาไว้ที่ `deleted_at` แถวยังคงอยู่ หน้าจอกรองออกให้เอง หากต้องการให้หายจากหน้าเว็บแต่ยังเก็บประวัติ ให้ใช้การปลดระวางแทน |
| เปิดกระทู้ที่ถูกซ่อนคืนจากหน้าจอไม่ได้ | ปลายทางบริการ `POST /api/boards/{board_id}/unhide` มีให้เรียกแล้วแต่ยังไม่มีปุ่ม ให้ใช้เครื่องมือฝั่งเทคนิคหรือแจ้งผู้ดูแลระบบ |
| ผู้ใช้งานรายหนึ่งเห็นเมนูไม่ครบทั้งที่ตำแหน่งถูกต้อง | ให้ตรวจรหัสสิทธิ์ของตำแหน่งใน `backend/config/roles.json` เทียบกับตารางรหัสสิทธิ์ในบทนี้ และตรวจสอบว่าแถวสมาชิกของผู้นั้นอยู่ในปีการศึกษาปัจจุบัน |
| ตั้งค่า `SUPER_ADMIN_ID` แล้วเหตุใดยังไม่มีสิทธิ์ | ค่านี้เป็นรหัสผู้ใช้งาน มิใช่รหัสนักเรียน และตั้งได้ครั้งละหนึ่งคน หากใส่รหัสนักเรียนลงไป ระบบจะไม่พบผู้ใช้งานคนนั้นแล้วข้ามค่านี้ไป |
